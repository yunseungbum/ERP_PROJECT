# Buddy FC ERP 프로젝트 개발 규칙

이 문서는 Buddy FC ERP 프로젝트의 기능 범위, 역할별 권한, 프론트엔드와 백엔드의 책임, 변수명 규칙 및 개발 협업 방식을 정의한다.

기능을 추가하거나 구조를 변경하기 전에 이 문서를 먼저 확인한다.

## 1. 사용자 구성

ERP 시스템의 기본 사용자 구성은 다음과 같다.

| 역할 코드 | 한글 역할 | 인원 | 설명 |
|---|---|---:|---|
| `President` | 회장 | 1명 | 전체 운영 현황을 관리한다. |
| `Coach` | 감독 | 1명 | 회원 출석과 경기 일정을 관리한다. |
| `Treasurer` | 총무 | 1명 | 회비와 재정 업무를 관리한다. |
| `InventoryManager` | 물품담당 | 2명 | 유니폼과 물품을 관리한다. |
| `Member` | 팀원 | 다수 | 허용된 정보를 읽기 전용으로 조회한다. |

한 사용자가 여러 역할을 가질 필요가 생기면 구현 전에 권한 구조를 다시 협의한다.

## 2. 역할별 기능 권한

권한 표기:

- `관리`: 조회, 작성 및 수정 가능
- `조회`: 읽기만 가능
- 삭제와 취소 권한은 아직 확정하지 않았으며 구현 전에 별도로 협의한다.

| 기능 | 회장 | 감독 | 총무 | 물품담당 | 팀원 |
|---|---:|---:|---:|---:|---:|
| 회원정보 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 참석현황 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 참석률현황 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 경기일정 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 유니폼 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 물품리스트 | 관리 | 관리 | 관리 | 관리 | 조회 |
| 지출내역 | 관리 | 조회 | 관리 | 조회 | 조회 |
| 회비 | 관리 | 조회 | 관리 | 조회 | 조회 |

화면에서 버튼을 숨기는 것은 사용자 편의를 위한 처리다. 실제 작성 및 수정 권한은 백엔드 API에서도 최종 확인한다.

## 3. 프론트엔드와 백엔드 책임

프로젝트는 프론트엔드와 백엔드를 분리한다.

### 프론트엔드

- 개발 도구: VS Code
- 기술: React, TypeScript, Vite
- 사용자에게 보이는 화면을 담당한다.
- 입력 폼과 기본 입력 검증을 담당한다.
- API 요청, 로딩 상태, 성공 메시지 및 오류 메시지를 처리한다.
- 역할에 따라 메뉴와 작성·수정 버튼을 표시하거나 숨긴다.
- 백엔드에서 받은 데이터를 화면에 표시한다.
- 회비, 예산, 권한과 같은 최종 업무 판단을 임의로 확정하지 않는다.

### 백엔드

- 개발 도구: Visual Studio
- 기술: C#, ASP.NET Core Web API
- Controller, Service 및 Data 구조로 나눈다.
- 프론트엔드 요청을 받고 처리 결과를 JSON으로 반환한다.
- 인증과 역할별 권한을 최종 확인한다.
- 업무 규칙과 금액 계산을 처리한다.
- 데이터베이스 조회, 저장 및 트랜잭션을 처리한다.
- HTML이나 React 화면을 만들지 않는다.

기본 요청 흐름:

```text
React 화면
→ 프론트 입력 검증
→ API 요청
→ Backend Controller
→ Backend Service
→ Backend Data/DB
→ JSON 응답
→ React 화면 갱신
```

## 4. 프론트엔드 입력 검증 원칙

필수 정보가 비어 있거나 명백히 잘못된 경우 프론트엔드에서 먼저 처리하고 API 요청을 보내지 않는다.

예시:

- 로그인 아이디가 비어 있음
- 로그인 비밀번호가 비어 있음
- 필수 회원정보가 비어 있음
- 필수 날짜나 금액을 입력하지 않음
- 숫자 입력란에 숫자가 아닌 값을 입력함
- 허용 범위를 벗어난 글자 수

로그인 예시:

```text
아이디 또는 비밀번호가 비어 있음
→ 프론트에서 입력 오류 표시
→ return
→ 백엔드 API를 호출하지 않음
```

정상 UI 흐름에서는 불필요한 요청을 보내지 않는다. 다만 브라우저 화면을 통하지 않은 직접 API 호출로부터 시스템과 DB를 보호하기 위해 백엔드의 필수값 및 업무 규칙 검증은 최소 방어선으로 유지한다.

## 5. 프론트엔드 폴더 구성 원칙

기능별 폴더를 만들고 해당 기능에 필요한 파일을 한 폴더에 모은다.

작은 기능에서 파일 하나마다 `api`, `hooks`, `types`, `components` 하위 폴더를 만들지 않는다.

로그인 기능 예시:

```text
src/features/login/
├─ LoginPage.tsx
├─ LoginForm.tsx
├─ LoginSuccessCard.tsx
├─ useLogin.ts
├─ loginApi.ts
├─ loginTypes.ts
└─ login.css
```

공통으로 사용하는 코드만 `shared`에 둔다.

```text
src/shared/
└─ api/
   └─ apiClient.ts
```

기능 파일이 많아져 한눈에 찾기 어려워질 때만 하위 폴더 분리를 제안하고 승인을 받은 후 변경한다.

## 6. 프론트엔드와 백엔드 변수명 통합

같은 의미의 데이터는 프론트엔드와 백엔드에서 동일한 영문 단어를 사용한다.

표기 방식만 각 언어의 관례를 따른다.

| 한글 의미 | React/TypeScript | C# | MySQL |
|---|---|---|---|
| 사용자 ID | `userId` | `UserId` | `user_id` |
| 로그인 아이디 | `loginId` | `LoginId` | `login_id` |
| 회원 ID | `memberId` | `MemberId` | `member_id` |
| 회원 이름 | `memberName` | `MemberName` | `member_name` |
| 역할 | `roles` | `Roles` | 역할 연결 테이블 |
| 납부 금액 | `paidAmount` | `PaidAmount` | `paid_amount` |
| 미납 금액 | `outstandingAmount` | `OutstandingAmount` | 계산값 또는 `outstanding_amount` |
| 경기 시작 시각 | `startsAt` | `StartsAt` | `starts_at` |
| 물품 이름 | `itemName` | `ItemName` | `item_name` |

명명 규칙:

- React/TypeScript 변수와 속성: `camelCase`
- React 컴포넌트와 TypeScript 타입: `PascalCase`
- C# 클래스와 속성: `PascalCase`
- C# 지역변수와 매개변수: `camelCase`
- MySQL 테이블과 컬럼: `snake_case`
- Boolean 값: `is`, `has`, `can`으로 의미를 명확히 표현
- 날짜와 시간: `At`, 날짜만 표현하면 `Date`
- 금액: 의미에 따라 `Amount`, 단가는 `UnitPrice`

변수명을 새로 만들거나 변경하기 전에 한글 의미, TypeScript 이름, C# 이름 및 DB 이름을 함께 확인한다.

## 7. 개발 협업 규칙

Codex는 프로젝트 개발을 보조하는 역할이다.

Codex는 사용자의 승인 없이 기능 전체를 임의로 구현하거나 구조를 대규모로 변경하지 않는다.

코드 변경 전 절차:

1. 구현하려는 기능의 목표를 설명한다.
2. 왜 해당 코드와 구조를 사용하려는지 설명한다.
3. 새로 만들거나 수정할 파일을 알려준다.
4. 프론트엔드부터 백엔드까지의 데이터 흐름을 설명한다.
5. 다른 선택지가 있으면 장단점을 설명한다.
6. 사용자의 승인을 기다린다.
7. 승인 후 코드를 적용한다.
8. 빌드, 린트 및 필요한 실행 테스트 결과를 설명한다.

단순한 오타 수정도 기존 동작에 영향을 줄 수 있으면 먼저 알린다. 읽기 전용 조사와 오류 원인 확인은 코드 변경 없이 진행할 수 있다.

## 8. 주니어 개발자를 위한 React 작성 원칙

- 처음에는 가장 단순하게 동작하는 흐름을 작성한다.
- 한 파일에 화면, API 요청, 복잡한 상태 및 업무 규칙을 모두 넣지 않는다.
- 반대로 짧은 함수 하나 때문에 불필요한 폴더와 파일을 만들지 않는다.
- React state가 왜 필요한지 설명한다.
- Props가 어느 컴포넌트에서 어디로 전달되는지 설명한다.
- API 요청이 시작되고 응답이 화면에 반영되는 순서를 설명한다.
- TypeScript 타입이 백엔드 DTO와 어떻게 연결되는지 설명한다.
- 새로운 React 문법이나 라이브러리를 사용할 때 사용 이유를 먼저 설명한다.
- 코드를 복사하는 것보다 사용자가 다음 기능에 재활용할 수 있게 설명한다.

기본 프론트엔드 흐름:

```text
Page
→ Form/Component
→ Hook
→ Feature API
→ Shared API Client
→ Backend API
```

기능이 단순하면 Hook이나 파일을 억지로 분리하지 않고, 분리했을 때 이해와 재사용에 실제 이점이 있는 경우에만 제안한다.

## 10. 현재 DB 로그인 단계

현재 로그인은 MySQL `users` 테이블의 고정 계정을 사용한다.

```text
president → President
director  → Director
coach     → Coach
treasurer → Treasurer
inventory → InventoryManager
member    → Member
```

원본 비밀번호는 코드와 DB에 저장하지 않고 User Secrets에만 보관한다. DB에는 ASP.NET `PasswordHasher`가 생성한 `password_hash`만 저장한다.

현재 포함:

- 프론트엔드 빈 값 검사
- 로그인 API 요청
- MySQL 활성 계정 조회
- 비밀번호 해시 검증
- 성공 사용자와 단일 역할 반환
- 잘못된 계정 또는 비밀번호 `401` 처리

현재 미포함:

- Access Token (구현 완료: 로그인 응답, 메모리 보관, 요청 헤더 자동 첨부)
- Refresh Token
- 새로고침 후 로그인 유지
- 서버 로그아웃 API
- JWT 기반 역할별 보호 API

위 미포함 기능은 각각 목표와 흐름을 설명하고 사용자 승인을 받은 후 단계별로 구현한다.

## 11. 로컬호스트 테스트 및 복구 규칙

- 프론트엔드와 백엔드의 로컬호스트 주소 및 포트는 프로젝트에 정한 기본 설정을 유지한다.
- Codex가 연결 확인을 위해 로컬호스트 주소, 포트, CORS 또는 API 주소를 임시로 변경했다면 테스트가 끝나기 전에 반드시 원래 설정으로 복구한다.
- 임시 테스트용 주소나 포트를 소스 코드, 설정 파일 또는 환경 변수에 남겨 두지 않는다.
- 테스트 종료 시 프론트엔드 API 주소와 백엔드 실행 주소가 서로 일치하는지 확인한다.
- Vite가 지정한 포트 대신 다른 포트로 자동 실행되어 연결 오류가 발생하지 않도록 `strictPort` 설정을 유지한다.
- 주소 또는 포트를 영구적으로 변경해야 한다면 변경 이유와 영향을 먼저 설명하고 사용자의 승인을 받은 후 적용한다.
